## Early signal worth discussing (source: RESULTS.md as of 2026-08-10)

sonnet5 bare: low 48+45=93, medium 54+42.4=96.4 (det PERFECT 54), high
32+45.8=77.8, xhigh 34+42.4=76.4, max 34+46=80. The deterministic half
collapses at high+ effort while the AI-judged half stays flat. Inference:
high-effort runs build more ambitious systems and break mechanical constraints
(truncation, determinism, self-tests, banned APIs) that medium respects, and
the judge does not punish that because F/G reward system depth. Before drawing
conclusions, read the .eval.json category breakdowns for s13/s14/s15 to see
which of A3/C/D/E actually failed.

## Review agenda

1. Keep the generation prompt hard (rabbit-hole traps) or tighten it?
   Tension: traps produce legible differentiation ("medium beats max" is
   itself a finding about effort calibration) vs the risk of measuring
   trap-dodging instead of capability. Lean (inference, not decided): freeze
   the prompt for the second pass so rows stay comparable; if a gentler or
   harder variant is wanted, fork it as eval02 rather than editing eval01 -
   editing the task invalidates every existing row.
2. Make RUBRIC.md more precise about the prompt's intent? Check: does the
   deterministic half already encode the traps fairly (it punishes
   truncation/Math.random/storage/missing tests); does F/G guidance let the
   judge reward 13 shallow systems over 8 real ones; is "stopped at a clean
   boundary with TODOs" (explicitly allowed by the prompt) scored
   consistently? Any RUBRIC/GRADER_PROMPT edit is a grader change: bump the
   version and re-grade everything you intend to compare (README rule).
3. Grader variance: 5 gradings per candidate exist - compute spread. If
   max-min per candidate exceeds roughly 4 points, consider a stronger judge,
   more gradings, or tighter GRADER_PROMPT output rules. Also decide whether
   to re-grade ALL candidates under fresh suffixes (f..j) with the fixed
   grade.sh so the plan-mode mixture disappears from the record.
4. Comparability ledger: mark every RESULTS row bare vs context-biased.
   Re-generate haiku and opus bare via generate.sh; keep the old
   context-biased rows as a separate "context impact" table - that contrast
   (bare vs CLAUDE.md-loaded) is itself an interesting result.
5. Deterministic-scorer robustness (tighten alongside RUBRIC if desired):
   C2 counts assertions by parsing rendered page text heuristically; D2/D3
   depend on a hash regex; find_button discovers controls by visible text and
   can miss custom UI; B4 is a PRNG hint list. Deterministic re-scoring is
   free, but re-score every candidate after any change so det numbers stay
   comparable.
6. Budget the full matrix from gen.json + RESULTS before launching opus/fable
   at max: sonnet5 generation ranged $1.10 (low, 4m31s) to $9.92 (xhigh,
   36m57s); t04 (opus xhigh, interactive) was $21 and 50m; grading is roughly
   $1 x 5 per candidate with the sonnet5-high judge.
7. Template extraction (secondary goal): write the eval01 pattern up as a
   checklist - frozen+versioned task prompt, deterministic scorer, blind
   parallel judge, N gradings averaged, provenance ledger, bare-env
   generation, resume-safe scripts. Candidate home: eval01/README.md section
   or TEMPLATE.md. Ties to the track03 "SDK agents with evals" module idea in
   ZACKSNOTES.

## Second-pass protocol (proposal - adjust during review)

1. Freeze generation prompt, RUBRIC, GRADER_PROMPT (bump versions if the
   review changed them). Pick ONE judge model+effort for the entire pass.
2. Generate all four models bare via generate.sh, distinct prefixes, keeping
   the .gen.json sidecars.
3. eval_ashfall.py over all candidates (runtime pass on).
4. grade.sh all candidates x 5 suffixes; sweeps are resume-safe (existing
   outputs skip; rejects park at .ai.json.rejected).
5. listscore.py per model; record rows plus provenance in RESULTS.md.
6. Commit and tag versions in the RESULTS header so the pass is reproducible.

## Lessons learned this session (feed the template writeup)

- Environment bias is mechanical, not hypothetical: interactive sessions load
  CLAUDE.md, skills, plugins, memory. Bare generation = claude -p with
  --safe-mode, empty temp cwd, pinned --permission-mode, prompt on stdin.
  generate.sh's header documents the full recipe and the reasons.
- ALWAYS pin --permission-mode in headless claude. Settings defaultMode=plan
  hijacked 6/25 judge sessions into "writing the plan file" (no JSON emitted);
  earlier, --permission-mode auto silently dropped a Write while the model
  claimed success. Verify side effects (file exists, output parses); never
  trust the reply text.
- Validate judge output with the same parser the pipeline uses downstream
  (eval_ashfall.load_ai), retry once, park rejects, and make sweeps
  idempotent (skip existing outputs) so re-running the same command is the
  recovery procedure.
- Byte-identical prompts plus staggered starts get server-side prompt-cache
  sharing across parallel runs; keep volatile bits (cwd) out of the system
  prompt (--exclude-dynamic-system-prompt-sections).
- Judges drift on output format even with explicit instructions; design the
  harness for non-compliance instead of assuming compliance.
- Hold the grader fixed and version every prompt; decide which comparisons
  matter BEFORE editing anything, because edits invalidate cross-version
  comparison.
